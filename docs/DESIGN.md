# 设计文档 · PT 保种组工资结算工具

这份文档说明**为什么这么设计** —— 硬件事实（站点怎么返回、税怎么扣）、取舍理由、
以及那些「看着多余其实是保命」的决定都在这里。使用说明见 `README.md`。

一句话概括：**工资是定额，考核只负责标记谁没达标；发放这件事要做到「怎么重跑都不会多发」。**

---

## 1. 计薪模型

```
方案（config.json → plans[]）     月薪（组员实收）
  3T   min_volume_tb: 3         200,000
  6T   min_volume_tb: 6         400,000
  12T  min_volume_tb: 12        600,000
```

没有折算公式，没有系数 —— 不存在「每 1 TB 给多少魔力值」这种算法。改薪只改一个数字，不动代码。

### 1.1 考核口径可配（单选 / 多选）

```jsonc
"assessment": { "metrics": ["volume"] }               // 只考体积
"assessment": { "metrics": ["count"] }                // 只考数量
"assessment": { "metrics": ["volume", "count"] }      // 两项都考，全达标才算达标
```

方案里的门槛字段跟着走：`min_volume_tb` / `min_count`。

**校验前置**：`metrics` 含体积但某方案没配 `min_volume_tb` → 启动即报错，不静默按 0 算。
`metrics` 里出现不认识的值 → 报错。方案 id 重复 → 报错。

### 1.2 明确不做的配置项

| 不做的字段 | 理由 |
|---|---|
| `plans[].term_months` | 只是公示信息，不参与任何计算 |
| `plans[].medal_bonus_pct` | 只是勋章效果说明，不参与计薪 |
| `plans[].name` | `id` 够了，多一个字段就多一处能写错 |
| `payout.salary_is` | 口径已定为「组员实收」，另一个分支是死代码 |
| `payout.rounding` | 固定向上取整，没有第二种选择 |
| `payout.min_gift` | 月薪量级远高于站点最小值门槛 |
| `assessment.under_quota_policy` | 固定「只标记，人工决定」 |
| `assessment.size_tolerance_tb` | 没用上 |
| `endpoints.admin_panel` / `admin_user` | 没有任何代码消费它，只用于打印链接 |
| `sites.json` / `plans.json` | 合并进 `config.json`，密钥靠 `.gitignore` 隔离 |

**原则：不参与计算的配置项一律不进配置文件** —— 每多一个字段，就多一处能写错、能让人误会的地方。

## 2. 考核表结构

组长人工维护的表，脚本按**表头名字**认列，列顺序随便动：

| UID | 检查日期 | 用户名 | 方案 |
|---|---|---|---|
| 10001 | 260815-3.560 TB | user001 | 3T |
| 10004 | 260815-5.645 TB | user004 | 6T ← **不达标** |
| 10007 | *(空)* | user007 | 12T ← **未测** |

要点：

- **`UID` 是唯一的必填列**，用户名可以整个不填（联网时从详情页自动取，**以站点为准**）。
- **第 2 列是复合列**：`日期-实测值`。日期只作留痕，实测值才是考核依据。
- **`方案` 是成员身份**，不是计算结果 —— 它决定月薪。
- 实测值来自 `userdetails.php?id=X` 页面自己加载的汇总行：`4893 条记录 | 总大小：51.510 TB`。
  `seeding_list` 接口仅作**详情页解析不出汇总行时的兜底**，可以不配。
  解析时只在含「条记录 / 总大小」的行上找，**绝不整页扫** ——
  详情页满页都是体积（上传量、下载量……），整页扫必错。

### 2.1 复合列解析规则

| 输入 | 解析 |
|---|---|
| `260815-3.560 TB` | 日期 260815，体积 3.560 TB |
| `260815-4893 条` | 日期 260815，数量 4893 |
| `260815-3.560 TB / 4893 个` | 两者都有 |
| `260815-3.560` | 裸小数 → 当体积（TB） |
| `260815-4893` | 裸整数 → 当数量 |
| 纯文字 / 空 | 什么都不认，不猜 |

**日期必须是 6 位或 8 位的独立 token**（`(?<!\d)…(?!\d)` 双边界）。
否则 `3.560` 里的 `3.56` 会被当成日期 —— 这个边界断言在自测里守着。

**体积必须带单位**（`[KMGTP](?:i?B)?`）。不加单位就不认，避免把「做种人数」当体积。

## 3. 结算流程

```
① 考核表（WPS / Excel，人工维护）
        ↓  直接读 .xlsx（zipfile + ElementTree，不需要 openpyxl）
② 计薪（查表）：方案 → 月薪定额
        ↓
③ 考核：实测值 ⚖ 方案门槛 → 达标 / 不达标 / 未测
        ↓
④ 反算赠送量：X = ceil((月薪 + tax_flat) / tax_rate)
        ↓
⑤ 工资表 CSV（列顺序对齐考核表，便于复制回原表）
        ↓  人工审核
⑥ 清单 dry-run：没月薪的跳过；不达标 / 未测的**列出来但默认不勾**
   （CLI 由 payout.include_unqualified / include_untested 决定要不要出现，默认不出现；
    界面上还多列一档「已发 n 次 / 发完」，发满 N 次的默认不勾）
        ↓  人工勾选 + 确认应赠合计
⑦ 发放：GET 赠送页现抓隐藏字段 → 逐笔 POST，≥10 秒/人，带留言
        ↓  每笔发出前数一遍「这人本周期已发几笔」，发满 N 次的跳过
⑧ 台账留痕（append-only，只追加 gift / reset 两种记录）
```

`--refresh` 可以插在 ① 和 ② 之间，联网抓每个人的当前做种汇总，
自动填 `measured_bytes` / `measured_count` 并按当期口径重写复合列文本。

## 4. 税收反算

接收者实收 = `tax_rate × 赠送量 − tax_flat`（实测：送 450,000 → 收 404,996）

要让对方**实收 Y**：

```
X = ceil((Y + tax_flat) / tax_rate)
```

| 月薪 Y（实收） | 需赠送 X | 校验 |
|---|---|---|
| 200,000 | **222,227** | 222227 × 0.9 − 4 = 200,000.3 ✅ |
| 400,000 | **444,449** | 444449 × 0.9 − 4 = 400,000.1 ✅ |
| 600,000 | **666,672** | 666672 × 0.9 − 4 = 600,000.8 ✅ |

**口径**：月薪 = 组员**实收**，脚本反算赠送量。另一个口径（送出 20W → 组员实收 179,996）
会让组员拿到的比承诺少，已排除。**向上取整，宁可多给一分，绝不少给。**

## 6. 发放限额与核对（10 秒限制的必答题）

**风险**：10 秒间隔 + 网络卡顿 → 「以为失败又发一次」重复发，或「实际成功却没记录」漏记。

**唯一的限额：每人每周期 N 次**（`payout.rounds_per_period`，界面「每 [单位] [N] 次」）。

| 机制 | 怎么算 | 挡住什么 |
|---|---|---|
| 发出前数一遍 | 每笔 POST **之前**读一次台账文件，数 `ledger.times_of(period, uid)`；`≥ N` 就跳过（`skipped_full`） | 重跑 / 手抖重点 / 双进程 / 断线续发，一次都不会多 |

这条判据**不依赖任何内存状态**（每次都重读台账文件），所以「点两次发放」「重跑命令」
「开了两个进程」都拦得住 —— 但只拦「超过 N 次」，不拦「N 次之内的重复」：
**N = 2 时同一个人点两次「发放」就是真的各领一笔**，这是设计如此。

`--force`（CLI）忽略这条上限，本周期发满的人也照发；界面上没有这个开关 ——
界面上要重发就走「重置周期」。

### 6.1 「已发几次」怎么算

`ledger.times_of(path, period, uid)` = 该 uid 在本周期 `status="ok"` 且**没被 reset 作废**
的 gift 条数。`ledger.period_state(path, period)` 给出汇总：

| 字段 | 口径 | 为什么 |
|---|---|---|
| `sent` | 本周期发出去的**笔数**（同一个人可以多条） | 「每周期 2 次」发满两轮就是 2 笔 |
| `total` | 本周期成功记录的金额合计 | 和 `sent` 同口径 |
| `uids` | `{uid: {times, amount, last_at, username}}` | 界面的「已发 n 次 / 发完」、发放前的跳过判断都读 `times` |
| `failed` | **有过失败记录、但一次都没成功**的 uid 数 | 补发成功后就不该再算失败；按记录条数算会把 1 个人报成 5 个 |

`ledger.reset_period(path, period, uids)` 回应「这些人发过了、但要让他们重新领 N 次」：
往台账**追加一条 `type=reset`**（带 `uids` 列表），不删历史。
`_alive()` 顺序扫一遍：reset 之后这些 uid 先前的 gift 不再算数，而 reset 之后新发的
以新的为准。**只作废列到的 uid**，没列到的一个字不动。

台账是 append-only 的 JSONL（`payout_ledger.jsonl`），只有两种记录，崩了最多丢最后一行：

```jsonc
{"v":1,"type":"gift","period":"2026-09","uid":10001,"username":"user001",
 "amount":222227,"plan":"3T","status":"ok","note":"跳到 do=transfer",
 "at":"2026-09-15T11:20:03"}
{"v":1,"type":"reset","period":"2026-09","uids":[10001],"note":"人工重置周期",
 "at":"2026-09-15T11:24:11"}
```

`status` 还有 `"fail"` 一档（记失败原因用），它**不计入 `times`** ——
所以发失败的人不占 N 次里的任何一次，可以直接续发。

### 6.2 失败绝不记账成成功

`judge_response` 的判定顺序（**只看落点 URL，页面文字一个都不看**）：

1. `status == 0`（网络异常）→ 失败
2. 响应像登录页 → 失败（登录态失效）
3. 认落点：响应里的 JS 跳转目标（`window.location.href`）+ 跟随 HTTP 重定向后的
   最终地址，两处取到的 URL 里找：
   - 命中 `gift_form.success_url`（默认 `do=transfer`）→ **成功**
   - 命中 `gift_form.duplicate_url`（默认 `do=duplicated`）→ 失败，**唯一可重试**
4. 都没命中 → 失败（判不出来就当没成，宁可少发不会错发）

**为什么不用文字判据**：赠送成功的响应里**一个字都没有**，只有一行 JS 跳转；
反过来，页面里还会碰巧带上「错误」「不能」这类宽泛词，先查失败标记就会把真成功
误杀。文字判据两边都不靠谱，所以整层不做。

碰到「人收到了、工具判失败」用 `payout.py --mark-paid <uid>` 人工补记
（金额照抄台账里的失败记录），**别直接重发**。判定失败的响应会原样存进
`samples/debug_gift_*.html`（cap 3），日志同时打印响应正文开头。

所以「站点改了返回结构」「隐藏字段没带上」这类问题，结果是**发不出去**（记 fail），
而不是「以为发出去了但没发」—— 前者只是白跑一趟，后者是真丢钱。

### 6.3 重试只给「确定没提交」的失败

`RETRYABLE_HINTS = ["重复提交"]` —— 只有站点跳 `do=duplicated`
（= 10 秒内重复点，站点自己说「这笔没送出」）才允许自动重试。

其余失败（网络中断 / 判不出落点 / 登录态失效）**一律不重试**：
它们都可能「其实已经提交了」，重试就是双倍发钱。

失败的人**不算已发次数**（`times_of` 只数 `status="ok"`），**但会记一条 `status=fail`**
（失败也要有账可查），重跑时自动补发，所以「不重试」不会让谁永远拿不到钱。

> 只读请求（抓体积）的重试是另一回事 —— 那种重试绝对安全，见 13.1 第 5 条。

### 6.4 核对信号

以**自己的 `Send gift` 流水**为准。同级及以上组员的魔力值流水看不到，只有余额，且余额有噪声。

## 8. 已确认的技术事实

### 8.1 体积单位（按 NexusPHP 源码核实）

- 除数固定 **1024**，进位阈值 **1000×1024^n**
- 后缀 `KB/MB/GB/TB/PB`，**也会短写成 `K/M/G/T/P`**
  → 解析正则必须是 `[KMGTP](?:i?B)?`，**且区分大小写**
  （加 `re.I` 会把种子名 `2160p` 的 `p` 当 PB，出天文数字）
- KB/MB/GB → 2 位小数；TB/PB → 3 位小数

### 8.2 汇总行写法

```
4893 条记录 | 总大小：51.510 TB      ← 经典 NexusPHP
94条记录，共计2.756 TB                ← 另一种模板（数字可能被 <b> 包着）
10 | 100 GB                           ← 通用管道符写法
```

解析不到汇总时，回退到逐行累加体积（`parse_seeding_rows`）。

**详情页专用解析** `parse_userdetails_seeding`：和列表页的 `parse_seeding_summary`
分开 —— 列表页整页扫没风险，详情页必须行内限定，两者不能共用一个函数。

### 8.3 后台走不通

`/nexusphp/user/users/{id}`：**同级（Administrator）及以上纯只读**，无任何操作按钮。
低一级（Uploader）才有「授予/修改/禁用/删除」。

所以发放只能走 `/mybonus.php` 赠送 —— **花组长自己的魔力值 + 10% 税**。

### 8.4 待现场验证

后台「修改上传量等」按钮里**有没有魔力值**。

- 有 → 对**低等级**组员可走后台发：**不花组长的魔力值、无 10% 税、无 10 秒限制**
- 只有「上传量」 → 老实走赠送

按 20 人测算，这一眼值 **733,430 魔力值/月**。

## 9. 输出格式约定

**前 4 列与考核表严格同序同名**，这样成品可以直接贴在原表右边：

```
UID | 方案 | 用户名 | 检查日期 | 体积 | 数量 | 方案要求 | 考核 | 月薪(实收) | 应赠送 | 差额 | 结果
```

- 考核表最低只要 `UID` 列；**用户名可选** —— 联网刷新时从详情页取，**以站点为准**
  （`nexus.guess_username_from_html`：页面里指向 `userdetails.php?id=<uid>` 的
  锚点文字就是当前用户名，用户改名后页面永远最新；没有锚点时用 `<h1>` 兜底）。
- `体积` / `数量` **恒显示**（抓取本就两样一起抓），体积单位在值里（`5.725T`）；
  考核口径（`assessment.metrics`）只影响判定和「方案要求」。
- `检查日期` 是**原始单元格文本**（联网算完写成 `260919-5.725T(1839)`），原样带出。
  冗余但有意：方便逐格回贴核对，也让表能直接反哺回考核表。
- `差额` 只在未达标时有值（`缺 0.355 TB` / `缺 7 个`），多选时用 `；` 连接多项。
- `结果` = **计算结果**（`settle._result_note`），列名就叫「结果」，只写数据不带状态字样
  （「考核」列已有）：`5.711 TB / 要求 3 TB` / `<失败原因>` / `没有方案：9T 不在 …`。
  它**不是**考核表那一列的照抄（考核表那边仍然认「备注」这个输入列名，
  见 `roster.COLUMN_ALIASES`）—— 抓取失败的行，结果就是排查线索（`HTTP 502`、
  `网络中断（URLError: …）`、`做种列表认不出汇总行（站点模板和解析对不上）`）。
- 界面列宽集中在 `PAY_COL_WIDTH`（③ 表用）+ `PAY2_COLUMNS`（④ 表用）。
- `结果` / `状态` 两列的宽度**按内容自适应**（`fit_column_width(texts, min, max)`，
  插完行 / 逐行刷新后重新量）：③ `PAY_NOTE_MIN~PAY_NOTE_MAX`（150~320px），
  ④ `PAY2_RESULT_MIN~PAY2_RESULT_MAX`（96~190px）、状态 66~150px。
  都 `stretch=False` —— 短内容不白占一长条，超长到上限后拖表格底部的横向滚动条。
- 编码 `utf-8-sig`，WPS / Excel 双击直开不乱码。

## 10. 站点适配层

### 10.1 为什么必须做

NexusPHP **没有统一的后台 URL**，查证结果：

| 版本 | 后台路径 |
|---|---|
| 经典 PHP 版 | 面板菜单存在数据库 `adminpanel` / `modpanel` / `sysoppanel` **三张表**里，入口文件随二次开发版本变化，无标准路径 |
| `xiaomlove/nexusphp`（Laravel + Filament） | 面板路径在 `AdminPanelProvider` 里配置，权限门槛由 `settings.system.access_admin_class_min` 控制 |

连站点安装目录都不一样 —— 有的在根目录，有的在 `/nexusphp` 子目录。
硬编码等于把工具锁死在一个站上。

**处理**：后台相关接口不做（没有代码消费），其余接口全部走 `config.json → endpoints`。

### 10.2 Endpoints 类的行为

模板占位符 `{uid}` / `{page}`，三种路径写法：

| 模板写法 | 解析结果 | 用途 |
|---|---|---|
| `mybonus.php` | `base_url` + `/mybonus.php` | 主站接口（`base_url` 可带子目录） |
| `/custom/u/{uid}` | `根域` + 路径 | 需要从站点根出发时 |
| `https://other.example.org/login` | 原样 | 完全外挂（如独立 SSO） |

**没配的接口调用时抛 `KeyError` 并在错误信息里指明去 `config.json` 补 —— 不瞎猜。**

经典 NexusPHP 的默认路径写在 `nexus.DEFAULT_ENDPOINTS` 里，`config.json` 只需写差异。

## 11. cookie 获取（`login.py` + `clipboard.py`）

只有两条路：

| 路 | 函数 | 何时用 |
|---|---|---|
| ① 账号密码登录 | `password_login()` | **不碰浏览器，浏览器开着也能用**。POST 登录表单，服务端 `Set-Cookie` |
| ② 剪贴板 | `clipboard_cookie_once()` / `from_clipboard_wizard()` | 兜底。F12 → Network → 复制 `Cookie:` 行 |

**粘贴来的 cookie 整行照收，不按名字筛** —— 各站 cookie 名五花八门
（老 NexusPHP 是 `c_secure_*`，新站是 `nexusphp_session` / `XSRF-TOKEN`），
按名字筛只会把真正的 session 筛没。校验只要求里面真有「名字=值」对。

GUI 的「获取cookie」按钮：剪贴板里已经有就**立刻**拿走写入（毫秒级，绝不轮询）；
没有 → 马上打开系统默认浏览器登录页，弹居中浮窗给三步指引。

**为什么不做「自动读浏览器 cookie」**（用 Chromium DPAPI + AES-GCM 纯标准库解密是可以的，
但不值得）：

1. 浏览器开着时 cookie 库被**独占锁住**，最常见的场景直接失败；
2. Chrome 127+ 引入 App-Bound 加密，密钥绑定浏览器进程，纯标准库彻底无解；
3. 各浏览器路径、profile、加密版本组合爆炸，维护成本远超收益。

复制粘贴一次 10 秒钟，比任何自动方案都可靠 —— 最坏结果是「发不出去」，不是「以为拿到了」。

**首次运行自举**：`config.json` 不存在时，自动从 `config.example.json` 复制一份再改；
图形界面还会顺手把 `roster.example.csv` 复制成 `roster.csv`，第一次打开就有能填的骨架。
所以 `python login.py` 永远是「一条命令直接可用」。

**uid 自动识别**：NexusPHP 的 `c_secure_uid` 就是 `base64(uid)`。解不出来时退化为
「请求裸 `userdetails.php`，从页面里出现最多的 `userdetails.php?id=N` 反推」。

## 12. 写配置：注释一行都不能少

`config.json` 是**手改的**，所以里面全是注释。可惜标准 `json` 模块
`loads → dumps` 一把梭会把注释、缩进、空行全冲掉。所以工具走**文本级定点替换**
（`nexus.patch_jsonc_value`），只有那一个值会被换掉，其余一个字节都不动。

要点：

| 机制 | 做法 |
|---|---|
| 认键 | 正则 `"键"\s*:\s*` 找候选，再用**字符串掩码**把「处在字符串字面量内部」的候选剔掉 —— 否则 endpoint 里的 `userid={uid}` 会被当成键 `uid` |
| 定位值 | `_scan_value_end`：标量到**行尾 / 逗号 / 右括号 / 注释开头**为止，对象和数组按括号配平扫 |
| **行尾注释** | 标量必须在注释前就停 —— 否则 `"uid": 0,  // 我的 uid` 里的注释会被值替换吃掉 |
| 排版 | `_format_json` 按**原缩进**递归排好，短标量数组（如 `["volume", "count"]`）保持单行 |
| 路径 | 支持点号路径（`assessment.metrics` / `payout.tax_rate`），逐层收窄搜索窗口 |
| 安全 | 同层同名键**必须唯一**，否则报错拒绝改动 —— 宁可不改，也不要改错地方 |
| 备份 | GUI 保存前自动写一份 `config.json.bak` |

`probe.py --selftest` 里有十几条断言守着这块（含「注释行数不变」「行尾注释没被吃掉」）。

## 13. 图形界面（`pt-seeder-settlement.py`）

**原则：界面只是一层壳。** 每个按钮背后调的都是 CLI 那套同一份函数，
台账也是同一个文件 —— **没有第二套逻辑**，界面里点一遍和命令行跑一遍结果完全一致。

用 `tkinter`：它是 CPython 标准库（官方安装包默认带），符合「零第三方依赖」这条硬约束。

### 13.1 线程与并发

1. **控件只能在主线程读**。tkinter 的 `Variable` 从后台线程 `.get()` 会抛
   `RuntimeError: main thread is not in main loop`。所以 `run()` 在**进线程前**
   把界面上所有值快照成普通 dict（`self.snap`），worker 只认快照，绝不碰控件。
2. **配置在主线程先存**。每个任务开始前先 `save_config()`，保证磁盘上的 `config.json`
   就是界面上的样子 —— 否则会出现「界面上改了但发出去的是旧配置」。
3. **耗时活儿放后台**。worker 线程把消息丢进 `queue.Queue`，主线程用
   `root.after(120, drain)` 取出来刷日志和进度条，界面不卡死。
4. **联网刷新本身也要并发**。抓一个人的耗时几乎全花在干等站点响应上，串行等于
   把这些等待一段段排起来。`refresh_measurements(workers=N)` 用
   `ThreadPoolExecutor` 把 N 个人的等待叠在一起（20 人 4 路 ≈ 快 4 倍）；
   每路**一条自己的 `Session`**（`session_factory` 造，不共用 cookie jar），
   每路仍按 `delay` 的节奏请求，站点承受的压力和串行时一样。
   `workers=1` 保持串行行为 —— 测试和命令行都走这条。
   并发时进度只在「抓完一个人」时报一次（`i` = 已处理完的人数），
   逐行刷新由 `on_member(member)` 回调驱动 —— 比「数同一个人报了几次进度」稳得多。
5. **只读请求要重试**。详情页和做种列表会偶发 `SSL: UNEXPECTED_EOF_WHILE_READING`
   （连接被掐断），并发时更频繁。`fetch_with_retry` 对**瞬时失败**
   （status 0 / 408 / 429 / 5xx）自动重试 2 次（间隔 1 秒、2 秒）；4xx 不重试
   （重试也没用）。只读请求重试绝对安全，**发放请求的重试是另一套规矩**（见 6.3）。
6. **「站点说没有记录」和「没抓到」必须分开**：
   · 响应里明确写「没有记录」/「没有做种记录」→ 真的 0 条，照记 0（0 必然不达标）；
   · 其余抓不到的情况 → `measure_error` 记原因（网络中断 / HTTP 码 / 登录态失效 /
     模板认不出），**实测列一律留空、状态按未测**，绝不悄悄写 0。

### 13.2 确认框：动手前的最后一次确认

CLI 靠 `--confirm`，界面靠一个把关键数字摆出来的确认框（**金额标红**）：

```
⚠ 这一下是真的发钱，发出去了收不回来。
  周期：2026-09
  人数：18 人
  应赠合计：6,222,309 魔力值      ← 红色加粗
                                  [取消] [确认发放]
```

不要求手输金额；红色大字就是为了**逼自己亲眼看一遍那个数字**。
另外「发放」按钮只在**赠送表单配全**之后才会亮 ——
`gift_form.success_url` 清空了，按钮永远是灰的。

按钮的亮/灰**每次勾选、每次保存配置都会重算**（否则填好表单、点了保存，
按钮还是灰的，人会以为没生效）。

**发放前不做任何预检**：点「发放」就直接逐笔试着发。先 GET 用户详情页
「确认登录态还活着」那种预检会把网络抖动、站点限流一股脑说成「cookie 已失效」，
误导排查；现在每笔的落点 URL 本身就说明了成没成，登录态失效的话第一笔就会报出来并停下。

### 13.3 勾选框（③④ 共用一套交互）

点格子切换、右键菜单「勾选 / 取消勾选 / 反选 / 全局反选」、底部「全选 / 全不选」。
右键的作用对象 = 当前选中的行；右键的那条不在选中集里就只改那一条（资源管理器习惯）；
「全局反选」无视选中集、整表一起翻。
**勾选状态只存在表格里，没有第二份副本** —— 所以不会出现「界面显示勾了、
实际发的是另一批人」这种错位。

「选中重算」认的是勾选框（兼容 Ctrl 多选）——**勾了谁就重抓谁**；
④ 页「能不能发」跟着勾选框实时重算。

### 13.4 清单里的「状态」「结果」两列与重置周期

④ 清单最后两列：**「状态」= 台账口径**（这个人**本周期**已经发了几次，整行上色）、
**「结果」= 这次点「发放」的结果**（`成功` / `失败` / `跳过` / `发送中…`，没发过是空的）。
分成两列是因为这两件事会不一致：**发失败的人「状态」还是「待发」**（台账里没有成功记录），
所以可以直接再点一次「发放」续发；而「跳过」的人是**已经发满 N 次**了。

| 值 | 条件 | 行色 | 默认勾选 |
|---|---|---|---|
| 待发 | 达标、本周期一次都没发（`times == 0`） | 橙 | ☑ |
| 已发 n 次 | 达标、`0 < times < N` | 绿 | ☑ |
| 发完 | 达标、`times >= N` | 绿 | ☐ |
| 不发 | 不达标 / 未测 | 红 | ☐ |

文案由 `payout.pay_state(times, limit)` 算（**只有这一处**，界面和命令行共用），
界面上包一层 `_pay2_state(it)` 只是因为要读界面上那个 N。

★ **「已发 n 次」是绿、默认还勾着**：「发过」不等于「不能发」—— N = 2 时第 2 次点
「发放」本来就该再发一笔。「发完」才默认不勾，但也只是「默认」：人想强制重发，
勾上照样发得出去（只是发出时会被逐笔跳过）。

行色由 `_pay2_tag(it)` **按更新后的那一行现算**（照 ③ 的三色风格）：本次结果 = `成功`
→ 绿；本周期发过 → 绿；待发 → 橙（发送中 / 发失败也在这档，还得人动手）；不发 → 红。
所以「发成功当场变绿」不管从哪条路回填都成立。

**两列的宽度都按内容现量**（`fit_column_width`）：状态 66~150px、结果 96~190px，
`stretch=False`。内容短就窄，变长了往上长，到上限后拖表格底部的横向滚动条。

发满 N 次的人也列出来靠的是 `plan_payout()` **不做事后去重**（`default_pick` 看
「达标 + 没发满」）；命令行同样列出来 —— 只是 `execute()` 发出前会逐笔跳过，
统计在 `skipped_full` 里。

**重置周期**（右键菜单 + 底部按钮）解决「这批人发过了、但要让他们重新领 N 次」：
调 `ledger.reset_period(led, period, uids)` 往台账**追加一条 `type=reset` 记录**
（带 `uids` 列表和备注），不删历史。`_alive()` 顺序扫一遍让这些 uid 先前的记录不再算数
（重置后又发的以新的为准）。重置后 `times_of()` 归零、状态回「待发」、又被默认勾上，
同时把 `items[i]["result"]` 清空（上次的「成功 / 失败」不该留在表上）。
**只动列到的那几个人** —— 别人一个字不改。

### 13.5 算工资页（③）的几个省事设计

1. **序号列**：③④ 表格第一列都是序号，方便对照着念「第几行是谁」；序号只在界面上，
   不进 CSV（CSV 要能直接贴回考核表）。
2. **缓存就是考核表本身**：每次算完把实测结果（用户名 / 检查日期）**写回 roster.csv**，
   下次打开界面直接载入它 —— 不用重算，也不再另存 payroll_cache.csv。
   「结果」列从来不进考核表 —— 那是现算出来的，写回去只会自我叠加。
   回写只支持 .csv（xlsx 只读）；按 **UID 对位**，只改用户名 / 方案 / 检查日期 /
   备注四列，表里多出来的列原样保留；抓失败的行**不写**（保住原值）。
3. **跑完自动勾上未测 / 不达标**（`_autocheck_bad`）：勾选在 ③ 页的语义就是
   「选中重算要处理的行」，自动勾好之后直接点「选中重算」把这些人重抓一遍 ——
   正好接上 13.1 的「抓不到就重试」。
   **「选中重算」重抓的是勾选的人，不看有没有数据**：勾上的行一律重新联网抓，
   抓不到就清空实测列、记「未测」（不留旧数字冒充刚抓到的）；
   **没 cookie 时抓不了，这时不动实测列**，只拿已有数据重算。

③ 表也是**整行上色**的三态（比 ④ 多留了一个颜色）：

| 状态 | 行色 | 为什么这么定 |
|---|---|---|
| 达标 | 绿 | 该发的人 |
| 不达标 | 红 | 判过的不达标 |
| 未测 | 橙 | **不是**达标、也**不是**判过的不达标 —— 差的是数据（登录态失效 / 抓取失败），重新抓一次就好，所以不跟不达标混成一片红 |

### 13.6 发放结果弹窗：三色数字 + 不动勾选

发完弹一个自绘的「发放结果」窗，成功 / 失败 / 跳过三个数各用一个颜色、各占一格：

```
发放结果
  成功        失败        跳过
  3 个        1 个        2 个        ← 绿 / 红 / 灰，15pt 加粗
  实发合计 666,681 魔力值
  ……（下面才是「谁还没发满 / 都发满了要重置」的说明）
```

三个数分开染色是因为它们**性质完全不同**：成功是真发出去的钱，失败和跳过都没发
（失败 = 判不出落点或站点拒绝；跳过 = 台账里已经发满了）。扫一眼颜色就知道这次
到底发成了几笔，不用去数日志。

弹窗里还有一句灰字：**「详情请确定后，查看清单。」**

点「确定」之后**什么都不做**：清单原地不动、勾选一个不动、「结果」留着。
发完只是**原地改表**：

- 每笔由后台线程经 `payrow2` 队列回填（`_payout_row_state(idx, 状态, 结果, 行色)`），
  主线程刷「状态 / 结果」两列；
- `done()` 里只做：写汇总 + 对一遍台账（`_sync_items_from_ledger`）+ 原地重绘
  （`keep_checks=True`，勾选按 uid 认回来）+ 重算汇总行；
- 顺带把 `items[i]["paid"]` / `items[i]["result"]` 更新掉，`_refresh_payout_summary`
  的「里面有 N 人本周期已发过」才是当场的真话。

重绘清单时**按 uid 认勾选**（不按行号）：`_render_payout_tree(keep_checks=True)`
从表格里收集已勾的 uid 再认回来 —— 清单顺序一变，按行号认会把勾落到别人头上。

## 15. 关键设计决策

| # | 问题 | 结论 |
|---|---|---|
| 1 | 月薪口径 | **组员实收** → 反算赠送量 222,227 / 444,449 / 666,672 |
| 2 | 不达标处理 | **列出来但默认不勾**，发不发组长拍。界面一律列出（看得见才好判断）；命令行默认不出现，要出现靠 `payout.include_unqualified` / `include_untested`（默认 false） |
| 3 | 配置分几个文件 | **一个** `config.json`；密钥靠 `.gitignore` 隔离，模板靠 `config.example.json` 开源 |
| 4 | 考核口径 | **可配**：体积 / 数量 / 两者；填几项就考几项，输出表也只出几列 |
| 5 | 输出格式 | 前 4 列与考核表同序（UID / 方案 / 用户名 / 检查日期），后面才是脚本加的列；用户名联网时以站点为准自动取 |
| 6 | 如何防重复发放 | **一层就够**：每笔发出前读台账数一遍这个人本周期已发几笔，`≥ N` 就跳过。**不逐人去重**，所以「点两次发放」在 N 次以内是**故意**要发的；台账 append-only，只追加 gift / reset |
| 7 | 怎么判断「发成功了」 | **只看落点 URL**：成功 = 跳 `mybonus.php?do=transfer`。响应里的文字一个都不看；`success_url` 清空 = 禁止真发 |
| 8 | 赠送表单字段 | **不写死在配置里**，每次发放前 GET 赠送页现抓 action + 隐藏字段 |
| 9 | 配置注释 | 保留。写配置走**文本级定点替换**，绝不 `json.loads → dumps` |
| 10 | 要不要做 GUI | 做。tkinter 是标准库，**零额外依赖**；但界面只是壳，逻辑仍只有一份 |
| 11 | GUI 怎么防手滑 | 确认框把周期 / 人数 / **应赠合计（红色加粗）** 摆出来，点「确认发放」即可（不要求手输金额）；表单没配全按钮就是灰的 |
| 12 | 浏览器自动读 cookie | **不做**：浏览器独占锁库 + Chrome 127+ App-Bound 加密 + cookie 名各异 → 统一复制粘贴整行照收 |
| 13 | 算工资的重复劳动 | 算完实测写回考核表（它就是缓存）、启动直接载入；改口径 / 想刷数据时点**「选中重算」**：勾上的行**全部重新联网抓一遍**，没勾的行一个字段都不碰 |
| 14 | 发放失败要不要自动重试 | **只重试「确定没提交」的**（站点限速页那类）；判定不明的失败一律留给人工核对 —— 重试就是重复发钱 |
| 15 | 发过的人要不要出现在清单里 | **两边都列出来**。界面状态「已发 n 次」绿、默认还勾着（N 次以内本来就该能再发）；「发完」也列出来、默认不勾。命令行同样列出，发出时逐笔跳过并统计 `skipped_full` |
| 16 | 怎么让这批人重新领 N 次 | **「重置周期」**（右键 / 底部按钮 / `ledger.py --reset-period --uid ...`）：台账**追加一条 `type=reset`**（带 uid 列表），只作废**列到的人本周期**的记录，历史一条不删 |
| 17 | ④ 清单为什么拆「状态」+「结果」 | 状态是**台账口径**（待发 / 已发 n 次 / 发完 / 不发），结果是**这次点「发放」的结果**（成功 / 失败 / 跳过）。发失败的人状态仍是「待发」，可以直接续发 —— 两件事合成一列会互相打架 |
| 18 | 结果弹窗点「确定」之后做什么 | **什么都不做**：清单原地不动、勾选一个不动、「结果」留着 |
| 19 | 结算周期的次数 / 周期键怎么生效 | **边打边生效**（不必先「生成清单」也不必存盘）：改 N 立刻重算**每行**的「已发 n 次 / 发完」，改周期键立刻按新周期对台账，填错当场在汇总行里报。实现 = 两个 `StringVar` 挂 `trace_add("write", …)`（`<KeyRelease>` 会漏粘贴和 IME 输入） |
| 20 | 「能发几次」以哪一处为准 | **只有 ④ 页顶栏那一格**：每行状态、发放前的跳过判断、台账弹窗、写进配置的值全读它 |
| 21 | 两张表的「结果」列给多宽 | **按内容自适应**：插完行 / 逐行刷新后用 `fit_column_width()` 量一遍，③ 150~320px、④ 96~190px，都不跟窗口拉伸 —— 超长到上限后拖横向滚动条 |

**待现场验证**：见 8.4。
